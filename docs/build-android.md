# Building and running on Android

Step-by-step account of what got this project onto a physical phone. Written assuming nothing — a fresh
machine, a fresh AI, or a forgetful future Wouter should be able to follow this cold.

## One-time machine setup

### 1. JDK 17 — exactly 17, not newer

Godot's Android Gradle build specifically requires **JDK 17**. Newer versions (21, 26) fail the build's own
version check. This is easy to get wrong: [adoptium.net](https://adoptium.net/temurin/releases/?version=17)
sometimes defaults its version dropdown to the newest release rather than 17 — **check the dropdown
explicitly says "17 - LTS"** before downloading, or you'll end up needing to install it twice, which is
exactly what happened here (JDK 26 got installed first by mistake).

Multiple JDKs can coexist on one machine — installing 17 doesn't require removing others.

### 2. Android Studio

Installed from [developer.android.com/studio](https://developer.android.com/studio) with default options.
**The installer alone is not enough** — the Android SDK, platform-tools (`adb`), and build-tools are
downloaded separately by Android Studio's own first-run setup wizard. Launch Android Studio at least once
and let that wizard finish (Standard install type) before expecting the SDK to exist on disk.

On this machine, that put things at:

- JDK 17: `C:\Program Files\Java\jdk-17`
- Android SDK: `C:\Users\Wouter Termaat\AppData\Local\Android\Sdk`
- `adb`: `<SDK path>\platform-tools\adb.exe`

### 3. Point Godot at both

**Editor → Editor Settings → Export → Android:**
- **Java SDK Path** → the JDK 17 folder above
- **Android SDK Path** → auto-detected correctly once Android Studio's SDK exists; confirm it, don't assume

These are stored in Godot's global editor settings (`%APPDATA%\Godot\editor_settings-4.7.tres`), not per
project — set once, works for every Godot project on this machine.

### 4. Install the Android export templates

**Editor → Manage Export Templates → Download and Install**, matching the installed Godot version exactly
(4.7.1.stable here). Confirmed by checking
`%APPDATA%\Godot\export_templates\4.7.1.stable\` contains `android_debug.apk` and `android_release.apk`.

## Project-level setup (done once per project, already committed)

### Texture compression — required or export fails outright

Android export **hard-requires** ETC2/ASTC texture compression support. Without it, export fails with:

> ETC2/ASTC texture compression is required for Android export.

Fixed by setting `rendering/textures/vram_compression/import_etc2_astc = true` in `project.godot`
(committed). If you ever see this error again, check that setting hasn't been reset.

### The export preset

Created via **Project → Export → Add... → Android**, then set:
- **Unique Name**: `com.woutertermaat.fallover`
- **Name**: `Fall Over`
- Architecture: `arm64-v8a` only (matches every realistic target phone; can widen later if needed)

Saved to `export_presets.cfg` at the project root, **committed to git** — see the decision below.

### Decision: `export_presets.cfg` is committed, not gitignored

The story that set this pipeline up (FO-006) flagged that the old `.gitignore` excluded this file because
export settings can carry keystore paths and passwords. Resolved here: **commit it.** For a debug-only
pipeline, the debug keystore uses Android's standard, publicly-known credentials
(`androiddebugkey` / password `android`) — there is no real secret in a debug config. Release signing is
explicitly out of scope for this story; revisit this decision if/when a release keystore is set up.

The keystore *file* itself (`debug.keystore`, auto-generated by Godot on first export at
`%APPDATA%\Godot\keystores\debug.keystore`) stays out of git — that's a per-machine file, not project
config, and `.gitignore` already excludes `*.keystore`/`*.jks`.

## Building and installing a debug APK

Godot can export from the command line without opening the editor:

```bash
"C:\Program Files\Godot\Godot_v4.7.1-stable_win64.exe" --headless --path "<project path>" --export-debug "Android" build/android/FallOver-debug.apk
```

`build/` is gitignored — build output never gets committed.

Install to a connected device:

```bash
"<Android SDK>\platform-tools\adb.exe" install -r build/android/FallOver-debug.apk
```

### ⚠️ Launching it from the command line needs the right component name

`adb shell monkey -p <package> -c android.intent.category.LAUNCHER 1` looked like it worked (no error) but
silently did nothing — focus stayed on the home launcher. The actual cause: guessing the launcher activity
class name and getting it wrong. Godot (non-Gradle export) uses `com.godot.game.GodotAppLauncher`, **not**
`com.godot.game.GodotApp` — the latter exists but isn't exported, so `am start` on it throws a
`SecurityException: not exported`.

Find the real one rather than guessing:

```bash
adb shell cmd package resolve-activity --brief <package_name>
```

This prints the actual exported launcher component. Then:

```bash
adb shell am start -n <package_name>/com.godot.game.GodotAppLauncher
```

## Enabling USB debugging on the phone (per device, once)

1. **Settings → About phone**, tap **Build number** 7 times → "You are now a developer!"
2. **Settings → System → Developer options** (location varies by phone brand) → enable **USB debugging**
3. Connect via USB, set the connection mode to **File Transfer** if prompted
4. Approve the **"Allow USB debugging?"** popup on the phone (check "Always allow from this computer" to
   skip this in future)
5. Confirm from the PC: `adb devices -l` should show the device as `device`, not `unauthorized`. If it
   shows `unauthorized`, the popup either hasn't appeared or hasn't been approved yet — unplugging and
   replugging the cable re-triggers it.

## What was actually verified

- Debug APK built successfully via command line (`--export-debug`)
- Installed on a **Google Pixel 9 Pro XL**, Android 17 (SDK 37), `arm64-v8a`
- FO-003's domino chain scene launched and displayed correctly on device (temporarily set as
  `run/main_scene` for this test, then reverted — the project's real main scene stays the FO-001
  placeholder until later stories replace it)
- **Touch input confirmed working**: tapping the screen triggers the first domino's impulse and the chain
  topples, exactly as on desktop
- The jitter noted in FO-019 (a fallen block failing to fully settle) is visible on this device too,
  confirming it isn't a headless-only artifact. Already tracked as a carry-over check for FO-004
  (does Jolt fix it), not something this story needed to resolve.
